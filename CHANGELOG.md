# Changelog

All notable changes to `json-api` will be documented in this file.

## [Unreleased]

### Added

- Package skeleton for Laravel 10 to 13 (PHP 8.1+), with a plain service provider and a publishable config file (`json-api-config`).
- Docker test matrix (`docker-compose.yml`) with one service per Laravel version (`l10`, `l11`, `l12`, `l13`).
- PHPUnit suites (`Unit`, `Feature`, `Contract`) running on Orchestra Testbench.
- Contract testing helper (`assertJsonApiDocument()`) backed by the official JSON:API schema.
- Static analysis (PHPStan + Larastan) and code checks (Pint).
- Configuration file `config/json-api.php` with sensible defaults, publishable with `php artisan vendor:publish --tag=json-api-config`.
- Every option can be set from `.env` (`JSON_API_*` variables), with boolean and integer conversion.
- Recursive configuration merge: an app that overrides only part of a group (for example `pagination.size`) keeps the remaining defaults of that group.
- `Settings` class: typed, always up-to-date access to the configuration, shared as a singleton.
- Configuration validation at boot: invalid values stop the application with an `InvalidConfigurationException` that reports every problem at once.
- `Pointer`: builds and reads JSON Pointers (RFC 6901) for the `source.pointer` of errors, with correct escaping of `~` and `/`.
- `MemberName`: converts attribute and relationship names between the configured style (`camel`, `kebab` or `snake`) and `snake_case`, for names and for first-level array keys.
- `MediaType`: strict reader, comparer and writer of a single media type, with `ext` and `profile` lists (RFC 7230 tokens and quoted values).
- `ContentNegotiator`: JSON:API 1.1 content negotiation rules for the `Content-Type` (415) and `Accept` (406) headers, with a strict and a permissive mode; unsupported extensions are rejected and profiles are ignored.
- Contract tests that pin what the official JSON:API schema accepts and rejects, documented in `tests/Fixtures/schema/NOTICE.md`.
- `Error` and `ErrorDocument`: immutable JSON:API error objects (`status`, `title`, `detail`, `code`, `id`, `source.pointer|parameter|header`, `meta`) and the full error document, always sent as `application/vnd.api+json`. With several errors the HTTP status is the shared one, `400` if they are all 4xx but different, and `500` if any is 5xx.
- `JsonApiException`: throw JSON:API errors from the app code (one or several, with their own headers). Client errors (4xx) are not written to the log; server errors (5xx) are, like any other exception.
- Error codes: a stable catalog with the `mundoprogra.json-api` prefix (`errors.code_prefix`), replaceable one by one with `errors.codes`, and switched off entirely with `errors.include_code`. Validation errors get one code per failed rule.
- Error texts (`title` and `detail`) in English and Spanish, in the current Laravel locale, publishable with `php artisan vendor:publish --tag=json-api-lang`.
- `ExceptionRenderer`, hooked into Laravel's exception handling from the service provider (same behavior from Laravel 10 to 13, no change to `bootstrap/app.php`, `Kernel` or `Handler`): every exception is rendered as a JSON:API error document, never as HTML. Covers validation (`source.pointer` / `source.parameter` per field), authentication (`401`, never a redirect), authorization, missing routes and resources, `405` with `Allow`, `429` with `Retry-After`, `419`, invalid signed URLs, `503` and any `abort(<status>)`. Server errors hide their internals unless `errors.expose_details` is on. Any `renderable` registered by the app wins over the package.
- Exceptions that cannot be modified (for example from a third-party package) are converted with Laravel's own `map()`; the package renders the result.
- Optional error `id` (`errors.include_id`, off by default): a unique id per error, sent in the response and added to the log context as `error_id`, so a reported error can be found in the app logs. The package only generates and hands over the id; it never writes or stores logs.
- `RequestScope`: a single rule that decides whether the package acts on a request (route marked by hand, `except`, request already asking for the JSON:API media type, then `mode` and `path_prefix` by whole segments). Outside the scope the package yields to Laravel (HTML, Laravel's own JSON, usual 404s) and does not note the `error_id` in the log. A `JsonApiException` thrown by hand is always answered as JSON:API.
- `ApplyJsonApi` middleware, added at the start of the global stack when the HTTP kernel is created (no change to `Kernel` or `bootstrap/app.php`) and available as the `json-api.apply` route alias: inside the scope the request asks for JSON:API, so `expectsJson()` is true and Laravel's `auth` middleware answers `401` instead of failing on `route('login')`. The original `Accept` header is kept on the request (`json-api.original_accept`). The alias marks a route by hand even outside the prefix or on an excepted path.
- `NegotiateContent` middleware (route alias `json-api.negotiate`): applies the JSON:API 1.1 content negotiation to the request. The `Content-Type` is checked only when the request has a body and its method is `POST`, `PATCH` or `DELETE` (`PUT` only with `allow_put`) and fails with `415`; the `Accept` is always checked, reading the original header the package kept, and fails with `406`. The error carries `source.header` and the specific reason in the app language.
- The content negotiation is applied on its own to every request inside the package scope, right after `ApplyJsonApi` at the start of the global stack (no change to `Kernel` or `bootstrap/app.php`). Outside the scope nothing is touched. Note: with `strict_headers` on (the default), a client sending `Accept: application/json` under the prefix now gets a `406`; set `JSON_API_STRICT_HEADERS=false` to accept plain JSON while migrating.
- `ResourceObject` (extends Laravel's `JsonResource`): a JSON:API resource object with `type` (the model table by default), `id` (the route key, always text), `attributes`, `relationships`, `links` and `meta`. Whoever writes a resource declares `jsonApiAttributes()` and, optionally, `jsonApiRelationships()`, `jsonApiLinks()`, `jsonApiMeta()` and `jsonApiRoute()`; `type()` and `id()` can be overridden. Attribute and relationship names are written in snake_case and converted to the `member_case` style (first level only); a name `id` or `type`, a repeated name, or a name shared by an attribute and a relationship is a developer error (`LogicException`). `null` values are kept, `when()` values that do not apply are left out, and empty members are omitted.
- A resource returned by a controller comes out as a JSON:API document: `jsonapi` (when `jsonapi_object` is on), `data`, and the members `with()` and `additional()` add (they can never override `jsonapi` or `data`), with the exact `application/vnd.api+json` `Content-Type`, `200`, or `201` plus a `Location` header when the model was just created. `withResponse()` still runs. A `204` has no `Content-Type` (Laravel's `response()->noContent()`).
- `links.self` is built from the short name of a route declared with `jsonApiRoute()`, with `links.route_name_prefix` in front, and left out if no such route exists. The links of a resource accept only `self`, as text or as a link object, as the spec defines; any other name is a `LogicException`.
- `Relationship::one()` and `Relationship::many()`: a relationship with its resource linkage (`type` and `id`), optional `links` (`self`, `related`) and `meta`. A relation that is not loaded is left out; a loaded but empty to-one relation comes out as `data: null` and an empty to-many as `data: []`.
- `ResourceObject::document()` returns the full document body as an array without needing an HTTP request (jobs, commands, tests).
- `ResourceObject::collection()` is refused with a clear error until collections arrive in a later phase.
- Contract tests build every resource document shape in each naming style, with and without `jsonapi`, and validate them against the official JSON:API schema.
- `QueryParameters`: the JSON:API query string of a request (`include`, `fields`, `sort`, `filter` and `page`) read into a typed, immutable structure that does not touch Eloquent. Field, relationship and sort names, and the first-level keys of `filter`, go from the configured `member_case` style to snake_case; `page[number]` and `page[size]` are positive integers and any other key of the `page` family is kept as sent. It only reads the query string, never the body.
- A malformed query parameter is a `400` error of the new `request.bad_query` family with an exact `source.parameter`, and every problem of the request comes out together in a single response. The reasons (malformed parameter, invalid name, empty list item, invalid page number or size, `include` too deep, unknown parameter) have their own texts in English and Spanish, which never repeat what the client sent. Names are stricter than the spec (letters, digits, hyphens and underscores, starting and ending with a letter or a digit) because they end up in Eloquent queries and URLs.
- `include` paths deeper than `query.max_include_depth` are rejected, and with `reject_unknown_query_params` turned on an unknown parameter made only of `a-z` is rejected too (names with any other character, such as `utm_source`, are implementation-specific and always ignored).
- `ValidateQuery` middleware, added on its own to every request inside the package scope right after the content negotiation (and available as the `json-api.query` route alias): a malformed query is a `400` before the controller runs, even if the endpoint does not use it. The parsed query is kept on the request and read with the `$request->jsonApiQuery()` macro, which parses it once per request.
- Sparse fieldsets: `fields[type]=a,b` makes a `ResourceObject` of that type let through only those attributes and relationships. `type`, `id`, `links` and `meta` always stay; a field that does not exist is ignored; an empty `fields[type]=` leaves the resource with no attributes or relationships; the order is the resource's and what was already omitted (a `when()` that does not apply, a relation not loaded) stays omitted. They only act inside the package scope: outside it the resource comes out whole and `fields` is ignored, even if malformed.
- `json-api` route middleware group: it puts together `json-api.apply`, `json-api.negotiate` and `json-api.query`, in that order, to give a single route outside the package scope the full treatment with `->middleware('json-api')`. Each of the three keeps its own alias, and `json-api.options` stays apart because it needs values (`json-api.options:per_page=25`). The alias that used to be called `json-api` (the `ApplyJsonApi` middleware) is now `json-api.apply`.
- `illuminate/auth` is now declared as a dependency, since the package uses `AuthenticationException`; a test checks that every `illuminate/*` package the source uses is declared in `composer.json`.
